# مخطط قاعدة البيانات وخريطة الحقول — «حقيبة المهام»

## 1. ملخص الجداول والعلاقات وأثر الحذف

تستخدم النواة معرّفات نصية ثابتة (`VARCHAR(64)`) موحّدة بين التخزين المحلي في المرحلة الأولى وقاعدة بيانات MySQL 8+ (`utf8mb4_unicode_ci`) في المرحلة الثانية، مع فصل التواريخ التي لا تتطلب وقتًا (`DATE`) عن المواعيد الزمنية (`DATETIME`)، وتخزين المبالغ الضريبية في نموذج 3A بالهللات الصحيحة (`BIGINT`).

```
organizations ──┬──< departments / authorities
                ├──< specialists ──< (tasks, documents, cases, case_sessions, poas, calendar_items)
                ├──< cases ──< case_sessions ──< tasks (session_id)
                ├──< documents ──< document_renewals (يحفظ التاريخ السابق والجديد)
                │               └──< tasks (type='تجديد', document_id)
                ├──< poas
                ├──< calendar_items (ربط اختياري بـ specialist_id وسجل تشغيلي)
                ├──< vat_3a_drafts ──< vat_3a_lines (amount_halalas, adjustment_halalas, vat_halalas)
                └──< share_logs (status='فُتحت المشاركة')
```

### قواعد أثر الحذف (`ON DELETE`)
- **حذف قضية (`cases`)**: تُحذف جلساتها المرتبطة (`ON DELETE CASCADE`) وتُفك ارتباطات المهام والتقويم (`SET NULL`) بعد عرض تحذير صريح باسم القضية وعدد الجلسات والمهام المتأثرة قبل التأكيد، وتُفضّل الأرشفة (`archived_at`) لحفظ التاريخ.
- **حذف وثيقة (`documents`)**: إذا وُجدت سجلات تجديد (`document_renewals`) يمنع المسار العلائقي (`ON DELETE RESTRICT`) ضياع التاريخ ويوجّه المستخدم إلى الأرشفة؛ وعند الحذف من المعاينة يُفك ربط مهام التجديد والتقويم (`SET NULL`) وتُحذف ملصقاتها.
- **تعديل تاريخ انتهاء الوثيقة أو تسجيل التجديد**: يُنشئ سجلًا مستقلًا في `document_renewals` يحتفظ بالتاريخ السابق والجديد والملاحظات والمحرر والتوقيت دون مسح السجل التاريخي.
- **حذف مختص (`specialists`)**: تُحوّل السجلات المسندة إليه إلى غير مسندة (`ON DELETE SET NULL`) مع عرض عدد السجلات المتأثرة قبل التأكيد.
- **حذف سجل مرتبط بملصقات (`labels`)**: تُحذف الملصقات التابعة للسجل المحذوف تلقائيًا، بينما تبقى ملصقات شاشة «اليوم» مستقلة.
- **حذف مسودة 3A (`vat_3a_drafts`)**: تُحذف بنودها تلقائيًا (`ON DELETE CASCADE`) بعد التأكيد، وتُحمى المسودات المؤرشفة بإعادة الفتح أو الأرشفة.

## 2. توسعة المرحلة الثانية (الحسابات والصلاحيات والمرفقات والتدقيق والإرسال الآلي)

تُضاف الجداول التالية في المرحلة الثانية دون كسر جداول النواة:
- **`users` و`roles_permissions`**: حسابات الدخول المرتبطة اختياريًا بـ `specialists.id`، مع صلاحيات مستقلة للعرض والتعديل والحذف والأرشفة والتصدير ووحدة الضريبة 3A.
- **`attachments`**: تخزين بيانات المرفقات المركزي (`entity_type`, `entity_id`, `file_path`, `mime_type`, `uploaded_by`, `created_at`) مع فحص الصلاحية عند التنزيل.
- **`activity_logs`**: سجل نشاط مركزي (`actor_user_id`, `action`, `entity_type`, `entity_id`, `diff_summary`, `created_at`) لتتبع الإنشاء والتعديل والأرشفة والحذف، وتُضاف خانة `version` على الكيانات التشغيلية لكشف تعارض التعديل المتزامن.
- **`automated_dispatches`**: طابور وجدولة الإرسال الآلي عبر واتساب للأعمال والبريد الإلكتروني، مع مفتاح منع التكرار المرتبط بالسجل والموعد وحالة التسليم.

## 4. قائمة التحقق لربط هوستنجر (المرحلة الثانية)

1. إنشاء قاعدة بيانات تجريبية على هوستنجر بترميز `utf8mb4_unicode_ci` وتنفيذ `001_init_haqibat_almaham.sql` ثم `002_seed_demo_data.sql` للتحقق من الفهارس والقيود.
2. استبدال `LocalStorageDataAdapter` بموصل الخادم (`HttpMySqlAdapter`) مع الحفاظ على أسماء الحقول والمعرّفات نفسها.
3. اختبار المسار المتكامل من الواجهة: إنشاء وثيقة ← إسناد مهمة تجديد لها ← تسجيل التجديد ← التحقق في MySQL ثم فتح السجل من جهاز ثانٍ للتأكد من ظهور المختص والتاريخين السابق والجديد.
4. اختبار كشف تعارض التعديل المتزامن، وتجربة أخذ نسخة احتياطية واستعادتها في قاعدة مستقلة قبل نقل أي بيانات فعلية.
